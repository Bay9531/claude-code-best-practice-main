# 框架系统为何重要

Claude Code 的功能为何不是"披着外衣的提示词"——以及框架系统才是区分玩具输出与生产级工程工作的关键所在。

## 执行摘要

Claude Code 经验丰富的用户中流传着一种常见的简化观点：*"技能、命令、子代理、钩子——它们最终都会变成模型的提示词，因此仅靠一个强大的提示词就足以达到同等效果。"*

在模型最终推理调用的层面上，这在技术上是正确的。模型只会看到令牌。

但在所有其他层面上——即实际软件工程发生的层面——**这种简化观点站不住脚。** 框架系统不是一个提示词投递系统。它是一个**提示词构建系统、一个确定性执行系统、一个上下文架构系统**——而这些能力是无法通过更强的措辞来替代的。

本报告阐述了这种简化观点在哪些地方是正确的、在哪些地方站不住脚，以及为何混淆"模型看到了什么"与"系统做了什么"会让实践者远离那些赋予 Claude Code 真正杠杆作用的功能。

---

## 听起来正确的简化观点

对于一个**单次原子任务**——"给我写一个递归斐波那契函数"——框架系统对输出质量没有任何贡献。将相同的令牌交给相同的模型，无论它们是通过技能、命令还是原始提示词到达的，得到的输出分布都是一样的。

在这个狭窄的范围内，简化观点成立：

> 输出质量 ≈ 提示词质量

这是 Claude Code 相比普通聊天机器人几乎没什么价值的范畴。这也是这种简化观点隐含假设的范畴——恰恰正是真实工程工作不属于的范畴。

---

## 简化观点在何处失效

框架系统的十项架构能力是在提示词无法触及的层面上运行的。

| # | 能力 | 功能 | 提示词无法复制的原因 |
|---|------|------|-----------------------|
| 1 | **上下文隔离** | 子代理在独立的上下文窗口中运行 | 一个提示词填充一个窗口。N 个并行子代理提供约 N 倍的有效上下文。 |
| 2 | **框架系统强制工具限制** | `allowed-tools` / `disallowedTools` 在模型使用工具前即拦截 | 提示词中的指令仅供参考；模型可以忽略。拒绝规则则无法忽略。 |
| 3 | **惰性加载规则与记忆** | `paths:` 前置元数据和子级 `CLAUDE.md` 文件仅在 Claude 触及匹配路径时加载 | 提示词是静态的——无法根据运行时读取的文件有条件地加载。 |
| 4 | **钩子：确定性代码执行** | Shell 命令在生命周期事件（PreToolUse、PostToolUse、Stop 等）时运行，并且可以**阻止**工具调用 | 提示词无法拦截自身的工具调用。即使模型"不想"执行，钩子也会执行。 |
| 5 | **模型路由** | `model: haiku` 或 `model: opus` 将调用路由到不同的模型端点 | 提示词中的任何令牌都无法改变哪个模型来回答。 |
| 6 | **并行性** | 多个子代理并发执行 | 提示词是顺序的。框架系统调度并行进程并收集结果。 |
| 7 | **跨会话持久性** | 记忆系统和设置层次结构跨对话持久保持 | 提示词在会话结束时消亡。 |
| 8 | **模块化系统提示词** | CLI 根据激活的功能有条件地加载 110+ 个系统提示词片段 | 用户无法手动编写或替换 CLI 的内部提示词片段。 |
| 9 | **技能预加载** | `skills:` 字段将技能的完整内容注入子代理的初始上下文 | 用户无法预先填充其他代理的上下文——只有框架系统加载器可以做到。 |
| 10 | **权限分类** | `auto` 权限模式使用后台分类器预批准或阻止工具调用 | 提示词无法为自身添加执行前安全层。 |

每一行都是一个维度，在这些维度上"强大的措辞"绝对无法替代。

## "提示词"一词的两种用法

这种简化观点利用了概念混淆。"提示词"一词被用来指代两种非常不同的事物：

| 含义 | 由谁控制 | 大小 |
|------|----------|------|
| (a) 用户输入的内容 | 用户 | 约 6–60 个令牌 |
| (b) 模型在推理时看到的内容 | 框架系统 | 约 5,000–50,000+ 个令牌 |

在聊天机器人中，(a) 和 (b) 是同一回事。
在 Claude Code 中，它们截然不同。

框架系统的工作恰恰在于使 (b) 远比 (a) 丰富：

```
用户输入："写一个递归 flatten 函数"                         ← (a) 约 6 个令牌

模型在推理时实际看到的内容：                                  ← (b) 约 15,000 个令牌
  ├── CLAUDE.md（项目约定）
  ├── 匹配的 .claude/rules/*.md（通过 paths: 前置元数据加载）
  ├── 模块化系统提示词片段
  ├── 工具定义
  ├── 环境上下文（当前工作目录、git 状态、平台）
  ├── 之前的对话历史
  ├── 模型通过 Read/Grep 工具读取的文件
  └── 用户的 6 个令牌请求
```

**输出质量是 (b) 的函数，而不是 (a) 的函数。** 框架系统构建了 (b)。"仅靠强大的提示词"无法重现 (b)，因为其中大部分内容并非由用户编写。

## 即便就输出质量而言，框架系统也在发挥作用

考虑同一个提示词——"写一个递归 flatten 函数"——在三种环境中：

| 环境 | 模型看到的内容 | 典型结果 |
|------|----------------|----------|
| 聊天机器人，无工具 | 一句话 | 教科书式递归，通用风格 |
| Claude Code，未读取文件 | 句子 + CLAUDE.md | 符合声明的项目约定 |
| Claude Code，代理循环 | 句子 + CLAUDE.md + 读取相邻文件 + 运行测试 | 符合实际代码库模式，通过测试，处理现有代码处理的边界情况 |

相同的模型。相同的用户提示词。**三种不同的输出质量。** 差异在于框架系统——具体来说，是它组装的有效上下文以及它支持的迭代循环。

对于非平凡任务，输出质量是以下因素的函数：

```
输出质量 = f(有效上下文, 模型能力, 迭代循环)
```

用户控制的*有效上下文*微乎其微（他们输入的提示词）。框架系统控制其余部分——以及整个迭代循环。

## 简化观点正确之处（以及错误之处）

| 论断 | 判定 |
|------|------|
| "在推理时，模型只看到令牌。" | ✅ 正确 |
| "技能、命令和子代理提示词都对某个上下文贡献了令牌。" | ✅ 正确 |
| "对于真空中的原子任务，提示词质量主导输出质量。" | ✅ 正确 |
| "因此，强大的提示词等同于使用各种功能。" | ❌ 错误 |
| "因此，框架系统对输出质量无关紧要。" | ❌ 对真实工程任务而言是错误的 |

前三项是准确的观察。跃迁到第四项是推理失败之处：它混淆了模型与包装模型的系统，并将原子任务与真实工程工作混为一谈。

---

## 正确的思维模型

> **提示词控制模型被要求做什么。**
> **框架控制系统在模型无法触及的层面上做什么**——在令牌到达之前、在令牌生成之后、跨会话、跨上下文以及跨进程。

功能不是带有额外步骤的提示词。它们是**框架系统层级的原语**——确定性执行、上下文架构和基础设施路由——在模型无权置喙的层面上运行。

一个有用的类比：

| 层面 | 聊天机器人 | Claude Code |
|------|-----------|-------------|
| 食谱 | 用户的消息 | 用户的消息 + 框架系统组装的上下文 |
| 厨房 | 无——只有一个学生 | 工具、钩子、记忆、并行工作器、生命周期事件 |

你可以写出世界上最好的食谱。但没有厨房，你无法大规模烹饪。

---

## 给实践者的启示

1. **对于原子问题，提示词质量几乎就是一切。** 框架系统无关紧要。如果这就是你所需的全部，使用聊天机器人即可。
2. **对于真实的代码库工作，框架系统在默默承担大量重担。** 推理时的有效提示词大部分是由框架系统构建的，而非用户输入的。
3. **利用功能来做提示词绝对做不到的事情：** 确定性（钩子）、隔离（子代理）、惰性加载（带 `paths:` 的规则）、持久性（记忆）、路由（逐代理的 `model:`）以及并行性。
4. **强大的提示词是必要条件，但不是充分条件。** 功能提供了提示词无法实现的确定性、隔离性和组合性。两者是互补关系，而非替代关系。
