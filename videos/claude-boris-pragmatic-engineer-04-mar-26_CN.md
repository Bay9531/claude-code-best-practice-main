## 访谈实录

[`0:00`](https://youtu.be/julbw1JuAz0?t=0) 我们来聊聊你的背景。你最初是怎么进入科技行业的？

[`0:08`](https://youtu.be/julbw1JuAz0?t=8) 我是从做我不该做的事情开始的。大概 12 岁的时候，我在 eBay 上卖宝可梦卡片，卖了一些之后，我意识到我还得把卡片寄出去。我不知道怎么寄东西——我还只是个孩子。所以我让我妈妈开车送我去邮局。我们到了那里，她在填邮寄表格，而我在想：我应该怎么收钱呢？eBay 上可以列出你的 PayPal——我当时没有 PayPal 账户。我记得看到 eBay 说"我们推荐使用 PayPal"。于是我在电脑上查了 PayPal，那是我第一次真正使用互联网去做一件有用的事情。我注册了，然后想：我怎么让钱从 PayPal 到我的口袋里？那时我才知道有借记卡这种东西。所以我妈妈开车带我去银行，我排队开了一个支票账户——他们给了我这个 12 岁的孩子一个支票账户和一张借记卡。然后我就想，好吧，我得把钱从 PayPal 转到银行。这需要一个过程。整个过程结束后，我收到了一张支票，存了进去，然后去取钱。自动取款机吐出了 20 美元。就在那一刻，我意识到：天哪，这太神奇了。你可以坐在家里的电脑前，做一些事情，然后自动取款机就会给你钱。这不是魔法，这背后是代码。

这就是我迷上编程的开始。我意识到如果我学会了编程，我就能在电脑上做任何事情来解决现实世界的问题。然后我开始学编程——从 TI-83 Plus 计算器开始。我有这款计算器，在代数课上我觉得做代数很烦人。所以我自学了如何在上面编程，写了一个解二次方程的求解器，然后传给全班同学。我们都得了 A，但后来被抓了，老师制止了我们。但你知道吗？这整个过程让我意识到我需要学习更多。

[`1:43`](https://youtu.be/julbw1JuAz0?t=103) 你是什么时候接触到编程语言和构建实际软件的？

[`1:49`](https://youtu.be/julbw1JuAz0?t=109) 之后我上了高中，继续学习 Visual Basic，然后是 Java。我自学了 Java，做了一些应用。在大学里我学了经济学，但花了很多时间学习函数式编程——Scala、Haskell 之类的。我创办了一个 Scala 俱乐部，做了很多 Scala 和函数式编程的工作。这最终让我写第一本书，关于 TypeScript。我确实在正式教育之外花了很多时间学习这些东西。

[`2:16`](https://youtu.be/julbw1JuAz0?t=136) 你大学毕业后加入了一家 YC 创业公司。能谈谈那段经历吗？

[`2:24`](https://youtu.be/julbw1JuAz0?t=144) 我经营了一年左右的自由职业，然后大学毕业后我加入了一家名为 Agile Diagnosis 的 YC 创业公司。这是一家医疗保健数据公司。第一周，CTO 对我说："这有一本 600 页的书，关于 HIPAA 合规。去读一下。"我读完了，然后我们弄清楚了如何合规。但这家公司当时遇到了困难。投资者要求我们以某种方式发展业务，把产品销售给医院系统而不是直接面向消费者。我们对这个方向不满意，所以作为创始人兼 CTO，他决定关闭公司。那时我们已经是盈利的，这一点很好。他给了我三个月的时间去找新工作。所以我开始找工——那时我还在为他的公司工作——同时还在下东区的一个共用工作空间里做自己的 startup。

[`3:12`](https://youtu.be/julbw1JuAz0?t=192) 之后你去了 Facebook，在 Instagram 团队工作。你是怎么进入 Facebook 的？那段时间你做了什么？

[`3:20`](https://youtu.be/julbw1JuAz0?t=200) 事情是这样的——我在共用工作空间做我的 startup，有个家伙走过来问我在做什么。我们聊了起来，他最后说"你应该来见见我的朋友们"。我去了，那是一间看起来像 Nike 商店的办公室。过了几周我才发现那其实是 Facebook。他们给了我实习机会，我加入了 Facebook 的广告 API 团队。我是 E4 级别加入的，一路晋升。这花了一段时间——我在 Facebook 待了大约 7 年。我做了一些事情：我写了一个框架，帮助公司统一代码质量指标；我创建了一个名为 Better Engineering 的程序——这是 Facebook 内部的一个内部创业项目，在公司内部推广工程最佳实践。我专注于代码质量和开发者生产力。这后来发展成一整套工具，帮助我们在 Facebook 的所有代码库中提升代码质量。最后我负责全公司的代码质量——所有 Facebook、Instagram、WhatsApp、Oculus 的代码库都是由我负责的。这包括了为数十亿用户服务的数亿行代码。

[`4:24`](https://youtu.be/julbw1JuAz0?t=264) 你在 Facebook/Instagram 有几次晋升，包括在 Instagram 的一个角色。这些机会是怎么来的？

[`4:32`](https://youtu.be/julbw1JuAz0?t=272) Instagram 被收购时我还是 E4。后来我成为 E5，然后是 E6、E7，最后是 E8。在 E6 到 E8 的阶段，我专注于工程文化和开发者生产力。我实际上搬到了日本，远程为 Instagram 工作了一段时间。我还在日本写了那本 TypeScript 书。我每天都在写这本书。那是一种非常不同的生活节奏——住在农村，骑自行车去农贸市场，完全不使用社交媒体。信息量非常少。我有很多时间深入思考。这是我生活中非常独特的一段时间。

[`5:15`](https://youtu.be/julbw1JuAz0?t=315) 是什么让你决定离开并在 Anthropic 开始新篇章？

[`5:20`](https://youtu.be/julbw1JuAz0?t=320) 在某个时候，我读了很多科幻小说。我在日本读的很多书都是科幻小说，我一直在想，如果 AI 出了问题，所有这些东西可能会变得非常可怕。我对此了解得越多，就越觉得我需要为此做点什么。我的意思是，这家公司以一种深思熟虑的方式来做 AI，而世界需要这个。所以最终我加入了 Anthropic。我原本并不打算构建一个产品——我加入是因为使命。但大约一年前，我确实推出了一款产品，这只是我们为了了解安全而在内部构建的一个小型研究原型。但团队真的很喜欢它，所以我开始在它上面投入更多时间。它最终成为了 Claude Code。

[`6:02`](https://youtu.be/julbw1JuAz0?t=362) 你一开始在 Anthropic 做什么？你是怎么从零开始推出 Claude Code 的？

[`6:08`](https://youtu.be/julbw1JuAz0?t=368) 我加入时还不知道自己要做什么。团队——Anthropic Labs 团队——才刚刚成立。我们想探索前沿。我花了大约一个月的时间在模型上做后训练，只是为了从研究的层面理解它是如何工作的。然后花了另外一个月的时间进行探索——构建各种奇怪的、稀奇古怪的原型。没有一个原型是为发布而构建的——只是为了了解模型能做什么。然后有一天，我构建了一个东西，它是一个使用终端的代理。我记得我给了它一个 bash 工具，然后我问它："我在听什么音乐？"它实际上去运行了一个 bash 命令来检查。那一刻我惊呆了。它找到了我正在听的音乐——Spotify 正在运行。我认为这是第一个迹象，表明这个东西可能变得非常特别。所以我继续在上面花时间。

[`7:00`](https://youtu.be/julbw1JuAz0?t=420) 当时你对产品的愿景是什么？你认为你想要构建什么级别的自主性？你想要多少个不同的代理？

[`7:10`](https://youtu.be/julbw1JuAz0?t=430) 说实话，我当时并没有一个清晰的愿景。我完全不知道这会发展成什么样，我只是觉得我抓住了一根线，我必须拽下去。我内心有种感觉，这是一种不同的产品形态。之前我们做编码的方式都是通过 Copilot：自动补全、聊天等。而这不一样——它是一个可以在终端里做事的代理。你描述你想要什么，然后它使用工具来实现。这是使用 AI 的一个完全不同的范式。而且从很早开始，我最大的问题就是我无法停止思考它。它占据了我所有清醒时的思维。我每天每夜都在想它。周末也在想。你想的就是"这东西能做什么呢？我怎么和它交互？它怎么和我交互？"

[`7:53`](https://youtu.be/julbw1JuAz0?t=473) 所以你是内部发布、观察反馈、迭代，然后才给予更多访问权限的？

[`8:02`](https://youtu.be/julbw1JuAz0?t=482) 在最初的几个月里，只有我在做这件事。它只是我电脑上的一个终端。我把它作为 CLI 运行——甚至不是守护进程状态——只是我在终端里跑的一个东西。没有人能访问它。然后我开始发一些 demo 视频，包括我刚才提到那个"我在听什么音乐"的视频。内部发帖后只有两个点赞。没什么反响。但那时公司里已经有大约 30 个人通过分享我的屏幕看到了它，他们很喜欢。他们说"你能帮我装一下吗？"然后他们开始使用它。这时我意识到这不仅仅是一个有趣的研究原型，它实际上对人们有用。所以团队开始增长——首先是一个由几个人组成的小型团队开始围绕它组建。然后在它成为公司内部更广泛使用的东西之后，更多人加入了。

[`8:48`](https://youtu.be/julbw1JuAz0?t=528) Claude Code 的名字是怎么来的？

[`8:52`](https://youtu.be/julbw1JuAz0?t=532) 最初它只是叫 Claude CLI。它只是一个 CLI 工具。然后我们改名为 Claude Code——用"Code"代替"CLI"——在 2025 年 2 月对外发布之前。

[`9:06`](https://youtu.be/julbw1JuAz0?t=546) 在 Claude Code 之前，你们有一个叫做 Clyde 的项目。那是关于什么的？

[`9:10`](https://youtu.be/julbw1JuAz0?t=550) Clyde 是一个内部编码助手——早于 Claude Code。它是一个在 Slack 中的机器人。你可以@它，它会尝试编写代码。它有很多问题——它是一个聊天机器人，所以它没有记忆，但团队做了一些非常有趣的工作。尽管 Clyde 从未发布，但它教会了我们很多。它教会了我们模型如何处理编码任务。在某种程度上，Clyde 是 Claude Code 的前身。

[`9:40`](https://youtu.be/julbw1JuAz0?t=580) 你们在最初的 Claude 编码产品中构建的体验，与现有的编码助手相比如何？你们在设计上必须做哪些不同的选择？

[`9:50`](https://youtu.be/julbw1JuAz0?t=590) 从一开始我们就有不同的理念。其他工具试图把模型放在一个盒子里——"这是你的应用，你需要这个组件，让它做这部分"——我们想要完全相反的效果。我们希望模型能够自由地使用它需要的任何工具，以任何它认为合适的顺序。所以终端是完美的选择。它是最开放的底层接口。你可以运行任何命令，做任何你想做的事情。没有限制。所以终端自然地成为了正确的起点。这不是为了限制模型——这是为了给它最大的自由度。然后我们添加了权限系统以确保安全。但我们故意在模型之上放了非常非常少的脚手架。

[`10:32`](https://youtu.be/julbw1JuAz0?t=632) 让我们谈谈 Claude Code 在 Anthropic 内部和外部的影响。它在内部广泛使用吗？帮助团队快速构建的激励结构是什么？

[`10:45`](https://youtu.be/julbw1JuAz0?t=645) 在 Anthropic，我们有一个原则，就是让我们的工具支持我们自己正在做的事情——这不是强制性的，但从文化上来说是高度鼓励的。在 Claude Code 团队，大约 95% 到 99% 的代码是由 Claude Code 编写的。我自己大概是 100%。我没有手动写过代码或者看了之后手动修改——但我会审阅。对团队中的很多人来说，这个数字在 95% 到 99% 之间，而且还在增长。我们鼓励团队使用 Claude Code 来编写他们的代码。我们发现在 Anthropic，我们的工程师比外部公司更早地采用了这些工作流程。所以我们内部使用这些工具的文化已经根深蒂固，这很棒。

[`11:23`](https://youtu.be/julbw1JuAz0?t=683) Anthropic 的代码审查流程是怎样的？采用率如何？你必须说服人们使用它吗？

[`11:30`](https://youtu.be/julbw1JuAz0?t=690) 我们的流程是：你编写代码——可能用 Claude Code 编写——然后它提交一个 PR。Claude 自动审查该 PR。它会逐行检查，找到问题，进行评论，然后开发者修复这些问题。然后还会有一个人工审查。这个过程非常快。我们能够在不影响质量的情况下加快速度。实际上我们可以在提高质量的同时加快速度，因为 Claude 覆盖了很多领域。这对开发者来说也是一个学习机会——当 Claude 审查他们的代码时，他们可以学习并成为更好的开发者。所以从文化上来说，这已经被广泛接受了。

[`12:12`](https://youtu.be/julbw1JuAz0?t=732) 你们有工程师在手动审查之前就合并 PR 的例子吗？还是说总是先有人工审查？

[`12:18`](https://youtu.be/julbw1JuAz0?t=738) 对于重要的东西——任何会投入生产或对用户可见的东西——我们总会在合并前做人工审查。对于原型和实验代码，如果它不会影响用户或生产，那么可以跳过人工审查。

[`12:32`](https://youtu.be/julbw1JuAz0?t=752) 你怎么处理 Claude 可能漏掉的问题或做出错误假设的风险？

[`12:38`](https://youtu.be/julbw1JuAz0?t=758) 最终用户是人，所以我们需要人来为最终结果负责。但我们已经设置了多层保护。第一是 Claude 编写代码。然后 Claude 审查自己的代码。然后是人审查。所有这些加在一起——瑞士奶酪模型——你得到的是一个相当稳健的流程。如果你愿意，也可以让人工审查在 Claude 审查之前进行。但我们在实践中看到，Claude 在代码审查方面非常出色。

[`13:10`](https://youtu.be/julbw1JuAz0?t=790) Claude Code 在发布前在 Anthropic 内部使用了多久？这个时间线是怎样的？

[`13:18`](https://youtu.be/julbw1JuAz0?t=798) 2024 年夏天我开始了第一个原型。2024 年 10 月/11 月前后，它在 Anthropic 内部更广泛地使用了。2025 年 2 月，我们向外部发布了。所以从第一个原型到对外发布大约是 8 个月的内部周期？不完全是这样——它有一个逐渐扩展的过程。和我一起工作的团队在 2024 年晚些时候开始使用它，然后在 Anthropic 内部更广泛地推广，最后才对外发布。

[`13:52`](https://youtu.be/julbw1JuAz0?t=832) 你现在怎么看 Claude Code 的权限系统？你在构建过程中学到了什么？

[`14:00`](https://youtu.be/julbw1JuAz0?t=840) 我们认为权限是 Claude Code 中最重要的方面之一。因为模型将使用工具运行命令——它很强大，但我们确保在用户的控制之下。我们有一个权限系统，你可以将其设置为在高风险操作之前自动接受或请求许可。你可以在大多数操作上设置自动接受，同时仍然对特定操作保留批准权。这种方法让我们在安全性和速度之间取得了正确的平衡。随着模型变得更加强大，权限系统也在不断演变。

[`14:40`](https://youtu.be/julbw1JuAz0?t=880) 你们有被称为"研究预览"的不同发布阶段。这些阶段意味着什么？

[`14:45`](https://youtu.be/julbw1JuAz0?t=885) 是的。我们认为对于 Agent 产品来说，逐步扩大范围很重要。我们从研究预览开始，这基本上意味着我们知道它并不完美，但我们已经做了足够的安全测试，相信让更多人使用它有助于我们学习并改进它。当我们的信心增强，产品更加成熟时，我们就会将其从研究预览中移出。但即使在研究预览阶段，它也被数百万人使用，所以我们认真对待这种信任。

[`15:20`](https://youtu.be/julbw1JuAz0?t=920) 你之前提到 Claude Code 的日活用户增长速度很快。是什么推动了这种增长，特别是最近？

[`15:28`](https://youtu.be/julbw1JuAz0?t=928) 增长一直很惊人。它从内部的一小部分用户开始，然后扩展到整个公司，再增长到全球数百万用户。但有趣的是，它并不是一夜之间发生的——尤其是对于非技术用户来说。许多早期的 Claude Code 用户是软件工程师。但随着时间的推移，我们看到了这种"潜在需求"——非技术用户也在使用它。他们用它来管理项目、分析数据、自动化任务。这启发了 Co-Work 的诞生，它将同样的代理能力带给非技术用户。Co-Work 是 Claude Code 发展的自然延伸。

[`16:02`](https://youtu.be/julbw1JuAz0?t=962) 你能谈谈 Claude Code 和 Co-Work 的产品技术架构吗？

[`16:08`](https://youtu.be/julbw1JuAz0?t=968) 当然。Claude Code 本质上是一个运行在终端里的代理。它是一个 CLI 工具。Co-Work 是建立在同一 Claude Agent SDK 之上的产品，但针对非技术用户做了调整并增加了安全防护。它们共享相同的核心技术——相同的模型、相同的工具使用能力、相同的权限系统。但 Co-Work 以一款桌面应用的形式提供，拥有更适合非技术用户的界面，运行在虚拟机上，并且有额外的安全防护。

[`16:40`](https://youtu.be/julbw1JuAz0?t=1000) 什么是 Claude Agent SDK？它和 Claude Code 有什么关系？

[`16:45`](https://youtu.be/julbw1JuAz0?t=1005) Claude Agent SDK 是一个底层库，提供代理功能——工具使用、与模型交互、处理上下文。Claude Code 是使用该 SDK 构建的产品之一。SDK 是抽象的，产品是具体的实现。随着时间的推移，我们正在将 SDK 中的更多功能直接构建到模型中。

[`17:10`](https://youtu.be/julbw1JuAz0?t=1030) 模型让 Claude Code 变得更简单或更困难的方式是什么？你们是否需要大幅改变产品的架构，或者说模型变得更好了？

[`1:24:00`](https://youtu.be/julbw1JuAz0?t=5040) 在那个小镇上，那是最酷的时刻。但实际上我意识到我完全不记得 TypeScript 了，因为那时我已经写了两年 Python。在某个时候，我创办了世界上最大的 TypeScript 聚会——在旧金山。我见到了很多我的英雄——Chris Cowell 写了反应式通用理论，Ryan Dahl 创造了 Node。那是我第一次深入这个社区，深入语言本身和工具本身。对于 TypeScript，类型系统中存在一种美——Hejlsberg 太聪明了，条件类型、字面类型——这些非常深刻的想法，即使是最硬核的函数式语言也没有，甚至 Haskell 都没有走这么远。Anders 把它推到了前所未有的高度。Joe Pamer 和其他人探索了很多这些想法。对他们来说这也是很实际的——他们有很大的非类型化 JavaScript 代码库，如何逐步迁移到类型化？你必须提出这些非常漂亮的想法来实现这一点。对我来说，Scala 是另一个我掉进去的兔子洞——函数式编程的世界。现在当我写代码、当模型写代码时，我仍然首先想到类型——类型签名比代码本身更重要，把它做对是关键。所以其中有美，有艺术。但最终它是实际的东西，是我们用来构建东西的东西——它是达到目的的手段，不是目的本身。我认为对我们此刻所处的这个时代，一个比喻是 15 世纪的印刷机。

[`1:25:57`](https://youtu.be/julbw1JuAz0?t=5157) 因为那时的情况很相似——有一群抄写员知道如何书写。

[`1:26:03`](https://youtu.be/julbw1JuAz0?t=5163) 那是一门需要学习的艺术。你需要学习，需要设备，可能需要赞助或被选中去练习，因为你需要一遍又一遍地复制同样的东西，很少人能这样做。我猜想这是高声望或高收入的。

[`1:26:24`](https://youtu.be/julbw1JuAz0?t=5184) 然后印刷机出现了。

[`1:26:27`](https://youtu.be/julbw1JuAz0?t=5187) 是的。在欧洲，你需要被领主或国王雇佣，经过多年的训练。有这样一个抄写员阶层，他们知道如何书写，被类似国王这样的人雇佣——国王或女王自己往往不识字。所以这是非常小众的技能，欧洲不到 1% 的人口识字。然后印刷机出现了。印刷材料的价格在接下来的 30-50 年里下降了大约 100 倍。印刷材料的数量在接下来的 50-100 年里增长了 10000 倍。这是第一个效应。识字率花了点时间才跟上——全球识字率上升到约 70%，但那又花了 200-300 年。因为学习阅读很难，学习书写很难，需要教育体系、纸墨基础设施、空闲时间——而不是在农场工作。需要工业化的早期阶段才能真正实现。但结果是，曾经锁在象牙塔里的东西现在对所有人开放。我们周围没有任何东西能在没有这点的前提下存在。如果我们都不识字，如果制造这个麦克风的人都不识字，就不可能有现代经济。这些事物都不存在。我想到，如果当时的人要预测印刷机之后会发生什么，没有人会预测到麦克风会出现。所以我觉得这是我们此刻所处时代最好的类比。

[`1:28:13`](https://youtu.be/julbw1JuAz0?t=5293) 有意思的是你说有些国王不识字却雇佣抄写员——因为如果坦诚地说，我们有企业主知道他们想构建什么，但雇佣软件工程师因为他们自己不会写代码。我们喜欢嘲笑那些带着画在白板上的原型过来说"这应该很容易"的 CEO——当然他们不理解有多难。这里有一个类比——有人想要他们想要的东西，但直到现在他们需要雇佣一个懂这个的专家来构建，想法和执行者之间总有脱节。就像印刷机一样，如果国王能自己读写信件，他们就不需要中间人，事情会更高效。当然对抄写员来说这不一定是最好的消息，但聪明的抄写员也可以做其他事——需要有人写书、运行印刷机等。

对，抄写员不再做抄写员了，但现在有了一类作家和作者。他们存在是因为文学作品的市场极大地扩展了。

[`1:29:30`](https://youtu.be/julbw1JuAz0?t=5370) 我想如果我们回到那时，抄写员的作品只有少数人阅读，有了印刷机后，作家多了，有些没多少人读，但有些有比以前更广的读者。因为印刷机，出现了新的职业。

[`1:29:44`](https://youtu.be/julbw1JuAz0?t=5384) 是的。

[`1:29:47`](https://youtu.be/julbw1JuAz0?t=5387) 最让人兴奋的是，今天完全无法预测在这之后会发生什么。没有印刷机，我们所知的经济就不存在。那么接下来会发生什么？什么是我们今天无法预测的、因为每个人都能编程而将存在的东西？

[`1:30:13`](https://youtu.be/julbw1JuAz0?t=5413) 我们无法预测，但我们可以看看现在什么在起作用。看看你周围——Anthropic 的软件工程师或构建者或技术人员——哪些人很突出？他们有什么技能？他们如何改变了工作方式？很难点名，因为这是我职业生涯中共事过的最强的人。有各种不同的类型。有些人是出色的原型师——把东西从零做到 0.5。有些人在寻找产品市场契合度方面很出色——做 0.5 到 1，或者从零到一。还有些人跨学科，我越来越多地看到这样的人——跨越产品和工程，或产品和设计，或设计和工程。我看到越来越多这样的混合型人才。

[`1:31:15`](https://youtu.be/julbw1JuAz0?t=5475) 从去年到今年，你的哪个信念改变了？你可能曾经相信、现在修正或抛弃的信念？

说实话，我不确定安全问题到底有多大。我加入 Anthropic 是因为我读了很多科幻小说，我知道如果出问题后果有多严重。但我不确定。从内部看到的情况，加上过去一年出现的新风险，让我更担心了。所以它曾经对我来说是很重要的事，现在变成最重要的事——如何确保事情往好的方向发展。

[`1:31:59`](https://youtu.be/julbw1JuAz0?t=5519) 可以说在所有 AI 事情开始之前你就是一个非常优秀的软件工程师，你似乎是一个非常高效的工程师——作为团队一员，也作为个人。有些技能在 AI 之前很宝贵，现在仍然同样宝贵甚至更宝贵，而有些技能可能不那么重要了，最好被抛弃？

那些最好被抛弃的：对代码风格和语言等的强烈看法。我等不及要超越这些无休止的语言之争和框架之争了。因为模型可以用任何语言和框架，如果你不喜欢，它可以为你重写。所以这不再重要了。今天仍然重要的是：有条理、以假设为驱动。在产品设计中这一点很重要——在这个一切都被颠覆的世界里，我们需要弄清楚下一步构建什么。在工程日常工作中也很重要——比如调试。你必须非常有条理。模型可以帮助很多，但我认为我们仍然处于过渡期，你仍然需要这些技能。我不知道 6 个月后你是否还需要。其他更有价值的技能：好奇心，愿意做超出自己领域边界的事情。如果你在做工程但又了解业务方面，你可以构建真正棒的产品。我认为下一个价值数十亿美元的产品，在 Claude Code 之后的下一个创业公司，可能就是一个人——有某个很酷的想法，他的大脑能够跨越工程、产品、商业，或设计、金融等。人们会变得越来越跨学科，这也会越来越被奖励。所以在某些方面，我认为这将是通才的一年。

另一个实际被奖励的技能是——注意力持续时间短。

[`1:35:25`](https://youtu.be/julbw1JuAz0?t=5725) 是的。最后，有什么书可以推荐吗？我掉进了一个兔子洞。刘慈欣——三体问题的作者——他其实还有很多其他很棒的书。我真的很喜欢他的短篇小说。对于刚接触科幻的人，或者想要更硬核科幻的人，我强烈推荐 Stross 的《Accelerando》。这本书基本上就是未来 50 年的产品路线图。它从起飞开始——接近 AI 奇点——最终以环绕木星的集体龙虾意识结束，太棒了。我认为它真正捕捉到的是这种越来越快的节奏感——与此刻的感觉非常契合。在技术方面，我强烈推荐《Scala 函数式编程》。即使语言选择已经不那么重要了，我认为函数式编程有一种艺术，教你如何写出更好的代码，教你如何用类型思考。如果你读这本书，重要的是要做练习。我完整做完了所有练习大概三遍，效果非常好——它真的把函数式类型这个想法敲进了你的脑子里，让你无法停止思考。
