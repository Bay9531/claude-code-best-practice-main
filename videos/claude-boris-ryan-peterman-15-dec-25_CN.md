## 访谈实录

[`0:02`](https://youtu.be/AmdLVWMdjOk?t=2) 模型变化太快了。如果你三个月或六个月后问我这个问题，我的答案会完全不同。这位是 Boris Cherny，Claude Code 的创建者，前 Meta 首席工程师。我们聊了塑造他职业生涯的一切。你能解释一下什么是"潜在需求"吗？

[`0:17`](https://youtu.be/AmdLVWMdjOk?t=17) 潜在需求我认为是产品中最重要的原则。

[`0:22`](https://youtu.be/AmdLVWMdjOk?t=22) 你说有一些明显的文化差异，那很困难。

[`0:26`](https://youtu.be/AmdLVWMdjOk?t=26) 天哪，"困难"太轻描淡写了。那简直就是噩梦。我们还聊了 Claude Code 以及 Anthropic 现在正在发生的事情。尽管 Anthropic 规模扩大了三倍，但每位工程师的生产力提升了将近 70%，这要归功于 Claude Code。不要为今天的模型构建，要为六个月后的模型构建。我会推荐给所有人的那本对我作为工程师影响最大的技术书是……你对与 Codex 和 OpenAI 的竞争有什么看法？我想从你职业生涯的起点开始聊——你在 Meta 晋升为高级工程师的故事。你当时在做什么项目？是什么让你得到了晋升？如果我没记错的话，项目是"聊天和群组"，这个项目是为了让 Messenger 和 Facebook 更紧密地结合。实际上，我在 Meta 的头几个项目都是关于 Messenger 和 Facebook 的。第一个大概是 Zuckerberg 的一个想法，关于同步 Messenger 聊天和 Facebook 群组。有几个这样的项目，试图让 Messenger 和 Facebook 更紧密。动机是，当时有一种感觉，这种公共空间的社交产品正在消失，事情正在向聊天和更随意的实时空间转移。我们尝试了几个版本的产品，聊天和群组是最终成功的那个。大概是第三个或第四个版本。我当时在 Facebook 群组团队，和 Messenger 团队在组织上距离很远。这个想法是当时的 PM Steve 提出的，我就抓住了它，说"太好了，我们来做吧"。然后我就开始 hack。很快就有了一些生命迹象。我申请了更多工程师，有三位工程师加入。然后我们获得了一些数据科学支持和设计支持。从网页端开始，后来也扩展到移动端。我们验证了这个想法：在 Facebook 群组里可以有聊天功能。但也有很多不顺利的地方，按现代标准来看体验非常粗糙。在那个年代，大家都在网页上构建，各种 bug 完全没问题。现在标准高多了。产品在增长，我们团队很小，每个人都要做所有事。我们没有用户研究员，所以午餐时我会去食堂，给食堂工作人员看新功能："你能找到怎么打开聊天吗？"有时候他们能找到，有时候找不到。这就是观察式用户研究。你看着人们在特定情况下如何完成任务，不给他们太多提示。你看他们在哪里卡住，他们能理解什么。我教会了团队这样做，很快大家午餐时都去食堂"骚扰"食堂工作人员，把他们作为代表性用户来测试。

有意思的是，早期 Facebook 的文化让工程师可以做代码之外这么多的事情。比如你在做用户研究，你还做了些设计，也指导别人做设计。这在 Facebook 文化中非常独特。我认为这非常重要。直到今天，在 Claude Code 团队——我所在的团队——我们非常重视通才。我喜欢和通才一起工作。如果你是一个会写代码的工程师，但同时也能做产品工作、设计工作、有产品感、愿意去和用户交流——我就喜欢和这种工程师一起工作。现在我们招聘所有职能都是这样。我们的产品经理写代码，数据科学家写代码，用户研究员也写一点代码。我喜欢这种通才。这是我成长的方式——从我 18 岁运营第一个创业公司起，我什么都要做。在 Facebook 之前我在小公司工作，什么都要做。在大公司你往往被迫进入自己的专属泳道，但这只是人为的。工程是什么？它是一套非常狭窄的技能，但你真正在做的是构建产品或基础设施，而这需要的远不止写代码。在 Facebook 这样奖励这种行为的地方工作真的很酷。在那个半年结束时我得到了晋升，接下来的半年里，团队里每个工程师也都得到了晋升。

在那些早期产品中，有一个你多次提到的概念——"潜在需求"。听起来这是很多产品方向的推动力。你能解释一下潜在需求吗？

[`5:42`](https://youtu.be/AmdLVWMdjOk?t=342) 潜在需求我认为是产品中最重要的原则。看看 Facebook 的成功产品，每一个都有潜在需求的元素。比如 Marketplace，它源于一个观察：当时 Facebook 群组中 40% 的帖子都是买卖东西。Facebook 群组不是为商业设计的，但人们就是用它来做这个。很酷的是，你设计一个产品时让它可以被 hack、被用户以某种方式滥用，然后你看数据，看他们是怎么滥用的，再围绕它构建产品。先是 Facebook 群组，然后是买卖群组，那显然成功了，因为人们已经想买卖东西了，然后是 Marketplace。这是同一个意图的自然延伸。Facebook Dating 也很类似——大约 60% 的个人主页浏览来自不同性别、不是朋友的人。所以这是一种传统的约会场景，但人们在互相窥视。产品原则是：你永远无法让人们做他们还没在做的事情。你能做的是找到他们已有的意图，引导他们更好地利用这个意图，更轻松地做他们想做的事。

在你的故事中，你提到你在跨组织工作，因为你需要连接 Messenger 和群组的工程工作。你说有一些明显的文化差异，那很困难。你对在非常不同文化的组织之间工作有什么建议？

[`7:30](https://youtu.be/AmdLVWMdjOk?t=450) 天哪，"困难"太轻描淡写了。那简直就是噩梦。Facebook 当时想要快速发布、快速推进产品。而 Messenger 只关心可靠性和性能。价值观完全相反。这不仅是文化上的工程师对工程师，而是那个团队的工程师对我们有戒心，因为我们会影响他们的性能指标。在组织上，他们的设置是为了缓慢发布而不影响指标，而我们的设置是为了快速发布。目标也完全不同——他们有 SLA 和正常运行时间，而我们只关心日活和参与度。这些文化价值观非常深层次。它们不只是人们谈论的东西，你可以从组织设计、目标设计等每个部分中看到。说实话，那个项目失败的原因之一——最终它演变成了一些成功的东西，但那个版本失败了——就是因为这种价值观差异。所以如果你想让价值观非常不同的公司成功合作，你必须找到某种共同的目标、共同的兴趣、共同的信念，一个如果他们合作测试会非常有趣的假设。聊天和群组这个功能对 Facebook 来说很酷，但对 Messenger 来说出于很多原因并不那么酷。以你现在的认知，回到那个项目你会怎么做？

[`9:10`](https://youtu.be/AmdLVWMdjOk?t=550) 我想我可能会直接去找 Zuckerberg 说：如果你真的认真对待这件事，我们应该把 Messenger 搬到 Facebook 的 org 里。这后来确实发生了，而且实际上发生了几次——Messenger 进了 org 又出来，又进去又出来。大公司就是这样。但要让这种事情成功，共同的汇报关系不能是像 Chris Cox 这样的级别，而应该稍微低一点，这样可以把组织构建得更协作一些。

[`9:39`](https://youtu.be/AmdLVWMdjOk?t=579) 明白了，对齐激励机制，就不会有那种不断的拉扯。

[`9:44`](https://youtu.be/AmdLVWMdjOk?t=584) 对，完全正确。在你的职业生涯中，我看到你做了很多有趣的副项目。我很好奇这些项目的蝴蝶效应。比如在加入 Meta 之前，你做了 Undux，一个 React 的状态管理框架。这对你的职业生涯有什么影响？

[`10:07`](https://youtu.be/AmdLVWMdjOk?t=607) 副项目对我来说非常重要。当我招聘工程师时，这是我一定会看的东西。我想要有副项目的人——酷的周末项目、有趣的副业，甚至是一个特别喜欢做康普茶之类的人。你想要那些普遍好奇、对主要工作之外的事情感兴趣的人。他们是全面发展的人，是我喜欢共事的人。我的很多成长就来自于这些副项目。Undux 的来由是：React 的状态管理完全不必要地复杂。当时的方案有 Flux，还有 Redux。我就是搞不懂 Redux。我自认为是个普通工程师——我构建产品，不是那种不可思议的系统工程师。对我来说，Redux 有 reducer 之类的东西，流程非常复杂，就是为了更新一点状态。我搞不懂。所以我构建了一个更简单的东西，似乎有效。我当时在一个非营利组织做志愿者，他们开始使用它，他们的工程师很喜欢。我加入 Facebook 后，看到很多关于 Redux 的 frustration，有一个内部群组，大家都在问和我一样的问题。当你遇到一个问题时，有时只是你一个人，但很多时候别人也有同样的问题。培养这种蜘蛛感应很重要——知道这个问题可能也是别人共享的。这绝对是一个共享的问题。我在支持帖子和团队的困难中看到了这一点。所以我在内部推出了 Unux。它还行，不算特别好，但至少比 Redux 好。在 Facebook 我不知道怎么推广它，所以我就发了帖子。一些人开始用。通知团队的 Jeff Case 是早期采用者，我们花了几个晚上调试一些棘手的通知相关 bug。我想获得更多采用，所以我写了一个脚本，抓取了报告问题的群组成员，按团队统计，然后通过聊天联系每个团队的技术主管和经理，为每个团队做一场技术分享。大概做了 20、30、40 场技术分享，在几周内。我骑着自行车穿梭在 Meta 园区做这些分享，非常有趣，因为人们很投入，他们很兴奋有人关心解决他们确实遇到的问题。在某个时候，Unux 是 Facebook 最流行的状态管理框架，然后很快被 Recoil 和更现代的替代方案取代，现在 Relay 之类的更流行了。这种副项目会出现在你的绩效评估中吗？在 Meta 的标准下，它算是一个加分项，但不是能让你晋级的核心因素。那时候我还有很多其他副项目。后来我迷上了 TypeScript。在前一家公司我们就在用 TypeScript，但好的资源不多。所以我就开始写一本关于它的书，因为我想"这事得有人做，还没有这本书太奇怪了"。这门语言太棒了，设计好得惊人。它有当时其他语言没有的想法——条件类型、字面类型、映射类型——这些是绝对疯狂的语言特性，即使是最硬核的 Haskeller 也会被震撼。但没人写这些东西。所以我深入进去写了这本书，它吃掉了大约一年的时间。不推荐，但深入其中真的很有趣。我还在旧金山创办了当时世界上最大的 TypeScript 聚会。那是一个很酷的机会去认识 Ryan Dahl（Node.js 创建者）等所有著名的 JavaScript 名人。这让我意识到，所有这些人都只是普通人，每个人都在做很酷的东西，任何人都可以做这些事情。

[`14:47`](https://youtu.be/AmdLVWMdjOk?t=887) 你在 Meta 或 Anthropic 后来用到了 TypeScript 或那种技术深度吗？有趣的是，我以前不在乎语言。大约 10 年前，我骑摩托车出了很严重的车祸，双臂都骨折了。

[`15:05`](https://youtu.be/AmdLVWMdjOk?t=905) 天哪。

[`15:05`](https://youtu.be/AmdLVWMdjOk?t=905) 两条手臂都断了。我打着两个吊带。大约一个月不能写代码，我的手还是很疼，所以写不了 JavaScript（我当时用的语言）。我不得不去学其他语言，因为它们用的击键次数更少。我从 CoffeeScript 开始，因为括号之类的少一些。这种语言现在可能已经不存在了。那也是我进入 Haskell 和函数式编程的原因——因为可以用更少的击键做同样的事情，这就是当时的动机。后来我在一家对冲基金工作，有一个同事 Rick 非常喜欢 Scala，他让我深入了解了 Scala 和函数式编程。直到今天，那本对我作为工程师影响最大的技术书就是《Scala 函数式编程》。你很可能今天不会用 Scala，但它教你思考编码问题的方式与大多数人在实践或学校中学到的方式完全不同，它会完全改变你编码的方式。对我来说，Scala、Haskell 和 CoffeeScript 是关键的第一步语言，然后是 Scala，然后是 TypeScript。这改变了我思考的方式——现在我编码时用类型思考，代码中最重要的是类型签名，这比代码本身更重要。把它做对了就能得到非常干净的代码。在 Facebook 我主要写 Flow 和 Hack，后来在 Instagram 写 Python，这都很有帮助。在 Anthropic 我主要写 TypeScript 和 Python，所以仍然很相关。但更大的教训是：用类型思考。

[`17:07`](https://youtu.be/AmdLVWMdjOk?t=1027) 在职业生涯的这个时候，你说你入职时被低估了，以中级工程师的身份加入，尽管你有丰富的经验。你说事后看来你很幸运被低估了。你是怎么想的？

[`17:23`](https://youtu.be/AmdLVWMdjOk?t=1043) 就是期望更低。在大公司，每个级别都有特定的期望——项目影响力和人员影响力等等。具体标准因公司而异。但很多是关于项目影响力和打勾清单之类的，这些都很花时间。所以被低估入职给了我探索的空间，让我可以为构建酷东西而构建酷东西。而且这也有助于建立势头——如果你以中级身份加入然后表现突出，每个人都觉得你很棒，给人留下很好的第一印象，这有助于建立好的声誉，给你未来更多的项目机会。我认为这是对所有公司的好建议——很多时候工程师换工作时会拼命要求升一级，但那样做有很多 downside。

来说说让你晋升到 Staff（E6）的那件事。你当时在哪里？是什么让你进入了更领导性的角色？当时聊天和群组已经发布了，有一个团队在做这个。我在加入 Facebook 前做过很多 JavaScript，但在 Facebook 我从来没写过 JavaScript，因为全是 PHP。我很想写 JavaScript。我们有网页界面。对 Facebook 群组来说，很多人用网页而不是移动端——比如群组管理员用大电脑和键盘更方便。当时网站很粗糙，是静态的 PHP 页面，JavaScript 零零散散地注入在各个地方，状态不一致，用户体验不好。我想用 JavaScript 重写它，但遭到了组织上的很多反对。主要原因是基础设施还没准备好。幸运的是，这时 Comet 开始了——这是 facebook.com 桌面版的重写项目。核心人员包括 Tom Occhino（现在在 Vercel）、Jing Chen 等人。我很想参与，所以我联系了他们，问怎么能帮上忙，并提出把 Facebook 群组作为 Comet 的试验田。我没有问任何人，就直接做了。后来我找到群组团队领导说："Comet 要来了，工作量很大。我们可以走在前头，为所有人设定标准，与其他团队建立关系。"我仍然遇到了很多反对："你不能放 20 个工程师在上面。"经过很多审查和争取，我们大概得到了 12 个工程师，因为这是一个很大的迁移，大概要一年。群组是整个 Facebook 中最大的产品面——这其实挺令人惊讶的。迁移基本成功了。除了建立关系之外，有趣的是我们影响了 Comet 的方向。对于一个基础设施项目，产品团队通常无法影响其方向，他们只是客户。但因为我们共同构建了它，我们构建了很多后来被其他团队使用的抽象。比如我特别记得 Relay mutations——发送 API 请求时需要一致性。有个 bug：你按下一个按钮，每次按下都发送一个 POST 请求，按钮状态切换。为了好的用户体验，一按下按钮状态就应该切换，这意味着需要乐观更新。同时当网络请求返回时，你也需要更新本地缓存以确保一致性。如果你不停按按钮，响应可能乱序到达，导致 UI 中的状态不同。于是我写了一个系统来队列化 mutations——以可靠性为代价的一致性——当时这是正确的权衡。所有人都用了这个系统。我就是这样认识了 relay 团队的人。这非常有趣。我一直喜欢那些深入一层去理解底层原理的工程师——产品工程师也可以构建基础设施，基础设施工程师也可以去和用户交流。对技术栈的其他部分保持好奇。

[`22:56`](https://youtu.be/AmdLVWMdjOk?t=1376) 你走在了 Comet 这个大型 JavaScript 重写的前面。你提到这给了你更多的控制权和优先机会。你说的是像这样构建对每个人都影响深远的基础产品组件吗？

[`23:21`](https://youtu.be/AmdLVWMdjOk?t=1401) 对，这是一个例子。另一个例子是 Comet 的质量比之前高得多，因为它是单页 Web 应用，感觉更精致。但我们还没在产品端定义清楚什么是质量。所以我写了很多笔记试图定义它，做了很多技术分享教其他团队我们学到了什么。你为这个 Comet 迁移申请了大量人力。我想知道如果用今天的工具——Claude Code——来做同样的评估，你觉得需要多少工程师来做那个 12 人的工作？

[`24:17`](https://youtu.be/AmdLVWMdjOk?t=1457) 整个迁移 Facebook 群组开始时是 12 个工程师，但最后可能用了 20-30 人，大约两年。现在的话，大概 5 个工程师、6 个月就够了。

[`53:16`](https://youtu.be/AmdLVWMdjOk?t=3196) 你提到了"反发布"。那是什么？反发布的想法是：如果你只向应用添加功能，对一小部分用户来说很酷，但对大多数不使用该功能的用户来说实际上是有害的。你可以想象一个只添加功能的应用，随着时间的推移，功能积累起来。如果每个功能被 10% 的人使用，普通用户会看到一堆他们不用的功能，显得杂乱和令人困惑。软件的屏幕是有限的空间，所有功能都在竞争这个有限的资源。添加一个功能就占用了用户可能使用的其他功能的机会。所以反发布是说，你需要设定某个使用率门槛，低于门槛就把功能删除。一小部分用户会不高兴，但对大多数用户来说是好的。

[`1:21:03`](https://youtu.be/AmdLVWMdjOk?t=4863) 有了 Claude Code，你觉得这对著名的"制造者日程 vs 管理者日程"有什么影响？听起来你说的软件工程师越来越像管理者风格——你有一队 Claude，不需要深度专注来推进，你需要的是在 20 个不同事物之间上下文切换。你不再有大的专注块来写代码了吗？不多了。我周末也会写代码——我喜欢安静的时间。但每天早上我打开 Claude Code——移动应用——现在 Claude 里有一个代码标签，这周刚刚发布，但我们用了很久了。每天早上我醒来启动几个 Agent 来开始我一天的代码。如果你 6 个月前问我这是不是我编码的方式，我会说"你疯了吗？这怎么行？"但它确实行得通。这就是我现在写很多代码的方式。我启动几个 Agent，然后在电脑上检查状态——如果代码看起来好就合并，有时候拉下来本地 teleport 编辑一点。你会和 Fiona 聊，据她告诉我她已经十年没写过代码了，但现在每周写好几次代码——即使作为经理她的日程非常疯狂——她可以用移动应用和网页，仍然可以打开终端让 Claude 帮她写代码。我们正经历这个转变——我们做的事、我成长过程中做的事正在彻底改变，而且它正在变得人人可及。

[`1:23:00`](https://youtu.be/AmdLVWMdjOk?t=4980) 最后一个问题。以你现在对整个职业生涯的了解，如果你能回到刚入行时给自己一些建议，你会说什么？用常识。[笑声] 大公司有很多让你远离常识的东西——有很多官僚组织架构。事情之所以是现在这样是因为它们一直是这样。有很多错位的激励。也有很多好的东西。但使用常识非常重要。早期职业生涯中我创办了几个创业公司，也在很多创业公司工作过。在那里也是一样的事情：用常识去弄清楚市场想要什么、用户想要什么，然后构建它。相信自己，培养自己的常识。
