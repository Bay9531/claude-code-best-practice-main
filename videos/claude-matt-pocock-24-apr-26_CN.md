### LLM 的限制：智能区与愚蠢区

所以我想首先谈谈 LLM 的那些奇怪限制，这些奇怪的限制正是我们很多工作必须围绕的基础。有一个叫 Dex Horthy 的人，他经营一家名为 Human Layer 的公司，他想出了这个想法：当你与 LLM 一起工作时，它们有一个**智能区**和一个**愚蠢区**。当你刚开始与 LLM 合作时，就像你刚开启一个新对话，从零开始。那是 LLM 能做最好工作的时候，因为在那种情况下，注意力关系是最不紧张的。

每次你向 LLM 添加一个 token，就像是向一个足球联赛添加一支球队。想象一下每次你向足球联赛添加一支球队时增加多少场比赛。它是以二次方规模增长的。这是因为注意力关系基本上从每个 token 到其他 token，涉及位置和单个 token 的含义。这意味着大约在 40% 左右——或者我认为大约 10 万 token 是我的新标记——因为无论你使用的是 100 万还是 20 万的上下文窗口，情况都差不多。它开始变得愚蠢。所以当你不断向同一个上下文窗口添加内容时，它变得越来越愚蠢，直到它做出愚蠢的决定。有过这种感觉的请举手。是的。酷。

所以这意味着我们希望将任务的大小控制在智能区之内，对吧？我们不希望 AI 贪多嚼不烂。这可以追溯到像 Martin Fowler 在《重构》中以及《程序员修炼之道》中提到的老建议——不要贪多嚼不烂。保持任务规模小，这样你作为开发者——人类开发者——就不会慌乱，不会进入愚蠢区。

### 多阶段计划和 Ralph Wiggum 循环

但是你如何处理大型任务？如何把一个像——我不知道——克隆一个公司或者做一些疯狂的事情这样的大任务，分解成适合愚蠢区的小任务？当然，一种方法是——我指的是 AI 公司可能希望你做的，或者自然的方式——就是一直继续、继续、继续。你最终进入愚蠢区，每次请求花费大量 token。然后你压缩回来。我们稍后会讨论如何正确压缩。然后继续、继续、继续，压缩回来，继续、继续、继续。我认为这不太有效，因为积累的沉淀物越多——我们稍后会讨论这个。

所以这里的理论是——这也是我一段时间以来一直在做的——我会使用这些多阶段计划，我说：好的，我们有这个四号任务，这个大型任务。让我们把它分解成小部分，这样我们就可以分块处理，在智能区中完成每一小块工作。以前使用过多阶段计划的请举手。是的，很常见的做法，对吧？这就是我们一直以来做事的方式。当然，这也是我在去年十二月之前一直在做的。

任何有自尊的开发者看到这个都会说："这是一个循环，对吧？这是一个循环。我们只是有阶段一、阶段二、阶段三、阶段四。为什么不直接用阶段 n？阶段 n 本质上就是——好的，我们有一个在后台运行的计划，然后我们就在上面循环，直到完成。"这就是——有人听说过 Ralph Wiggum 作为一种软件实践吗？好的，酷。没听说过 Ralph Wiggum 作为软件实践的请举手。实际上，这样更像是这样。好的。所以有一个叫做 Ralph Wiggum 的想法，嗯，基本上是基于这个——本质上你需要做的就是指定旅程的终点，你说好的，我们创建一个 PRD（产品需求文档）来描述我们要去哪里，然后你对 AI 说，做一个小修改，再做一个小修改，一步步接近目标。Ralph 的效果还可以，但我更喜欢多一些结构。这就是我们在思考智能区方面的进展。

所以先讲糟糕的代码。图在哪里？在这里。在他的书《软件设计哲学》中，John Ousterhout 谈到了理想类型的模块。想象你有一个看起来像这样的代码库。这里的每个方块都是单独的文件。这些文件导出东西。它们有你可以从文件中拉取然后用在其他东西中的东西。所以你可能有一些奇怪的依赖关系——这个文件可能依赖这个文件或那个文件。

现在，如果这些文件很小，而且它们不导出很多东西，John 会称这些为**浅层模块**——它们看起来像这样。如果我实际——不，我画不出一个好的图。它们基本上是很多小块。这对 AI 来说很难导航，因为它不真正理解所有东西之间的依赖关系。它无法弄清楚所有东西在哪里。它必须手动追踪整个图，然后——好的，这个依赖这个，这个依赖这个，这个依赖这个。

而且这也很难测试，因为你在哪里划定测试边界？你是单独测试每个模块？就像直接画一个测试边界。不，别那样做。围绕这个画一个，然后可能围绕下一个画另一个测试边界，再下一个，或者你应该做大组的测试？你应该说，好的，我们把这些相关的模块一起测试，然后——你知道——祈祷它们能工作。

这意味着，如果我认为糟糕的测试大多看起来像那样——AI 基本上试图把每个小函数包裹在自己的测试边界中，然后单独测试它们。但这意味着，当这个模块调用那两个——所以它依赖这两个——那么这个模块可能会错误排序函数，或者那个糟糕的模块内部可能有值得单独测试的东西。然后如果你在这个外面包裹一个测试边界，你会怎么做？你 mock 其他两个模块？那怎么行？所以实际弄清楚如何构建一个易于测试的代码库是至关重要的，因为如果我们的代码库易于测试，那么我们的反馈循环会更好，AI 会在我们的代码库中做更好的工作。有道理吗？

那么好的代码库长什么样？不像那样。它像这样——你有 John Ousterhout 所谓的**深度模块**。这些模块有一个小接口——暴露一个小的简单接口——内部有大量功能。这意味着它们很容易测试，因为——假设这个和这个之间有依赖关系。我的箭头有用吗？是的，好了。那么你要做的就是在那个模块周围包裹一个大测试边界。你会抓住很多好东西，因为你在测试很多功能，而调用模块的人将有一个简单的接口。所以不会太复杂。有道理。深度模块与浅层模块。好的是这个。浅的版本是坏的。

我发现，如果不加引导，或者你不小心看管 AI，它会产生像这样的代码库。所以你在指导它的时候要非常非常小心。这也是为什么——如果我们看看 PRD——PR 去哪了？它在 issue 里面。在游戏化系统里面。没有找到。当然没有。在这里。那么我有——在这里面——数据模型，模块。所以它特别说明——好的，这个游戏化服务是一个新的深度模块，我们将围绕它进行测试。它会有这个特定的接口，它会——好的，我们也在修改进度服务。我们修改课程路由，修改仪表盘路由等等。所以，我对我正在编辑的模块非常具体，我确保在整个计划以及整个实施过程中，我在心中保持那个模块地图。有道理吗？非常非常有用。

它还有另一个用途。它不仅让你的应用更可测试，而且你还可以做一个心理技巧。在我告诉你们那是什么的时候，我要加满水。嗯，让我从你们那里收一个问题。觉得比以前用 AI 工作更辛苦的请举手。是的。嗯，觉得不如以前了解自己代码库的请举手。是的。这是真实的。因为我们在快速前进，我们在委托更多的事情，我们最终失去了对代码库的感觉。如果我们失去了对代码库的感觉，我们就无法改进它。我们基本上是把它的形状委托给了 AI。我认为那不好。

但那么，我们如何才能在快速前进的同时，在脑海中保留足够的空间？我认为这是一种方法——你在做的不仅仅是思考在你的代码库中创建大块、大服务。我认为你应该做的是——**为这些模块设计接口，但把实现委托出去**。换句话说，这些模块可以变成灰盒——你只需要知道它们的形状。你需要知道它们做什么以及它们如何表现，但你可以委托这些模块的实现。我发现这非常好。我不一定需要共同审查那个模块内部的每一件事。我不一定需要知道它在做什么的一切。我只需要知道它在某些条件下表现某种方式，并且它做它的事。所以，这有点像——好的，我对我的代码库有一个大致的了解，我知道里面的形状，我知道所有接口做什么，但我可以委托里面是什么。我发现这非常好——既能保持我对代码库的感觉，又能保持我的理智。有道理吗？

### 改进代码库架构技能

### Sand Castle：并行 AFK 循环

实际上，嗯，是的，让我们趁热打铁。我最近花了——嗯，大概一周左右——构建了这个叫做 **Sand Castle** 的东西。Sand Castle 是我对现有的 AFK 代理运行选项不太满意。它的作用是——它基本上是一个 TypeScript 库，用于运行这些循环。所以你有一个 run 函数，创建一个工作树，在 Docker 容器中沙盒化它，然后允许你在里面运行一个提示词。在那个工作树中，它只是一个 git 分支，你有那些代码，然后你可以稍后合并它。

如果我打开——有一些非常非常好的查看方式，它基本上让你运行这些自动循环，并且允许你非常简单地跨多个不同的代理进行并行化。所以我会进入我的 sand_castle 文件，进入 main.ts，让我们快速过一遍。所以这有点像我之前展示给你们的 Ralph 循环的一个版本。这是我们把顺序变成并行的。

我们这里首先有一个规划器，它有一个计划提示词，查看积压并选择一定数量的 issue 来并行处理。还记得我给你们看的那个有所有阻塞关系的看板吗？它计算出所有阶段。所以这个会说——好的，假设我们有——你可以忽略所有这些胶水代码。这基本上就是一组 issue——GitHub issue——带有一个标题和一个供你工作的分支。然后对于每个 issue，我们创建一个沙盒，然后我们在那个沙盒中运行 implement，传入 issue 编号、issue 标题和分支。这就像我们刚才运行的循环。
